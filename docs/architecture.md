# Architecture

`pi-agents` has three dashboard process roles: one frontend, one daemon for a state root, and one worker for each live session. Each worker starts a separate installed `pi` child. The daemon owns durable dashboard state. Pi owns the agent and its canonical session file.

## Process roles separate the interface, state, and Pi lifetime

### The frontend handles terminal input and rendering

[`bin/pi-agents.mjs`](../bin/pi-agents.mjs) selects one state root before loading the command-line interface. With no command, [`runDashboardApp`](../app/standalone.mjs) connects to or starts the daemon and opens [`createStandaloneList`](../app/list/standalone-list.mjs).

The frontend renders the list and viewer. It sends version 1 requests over the daemon's Unix socket. It does not write session records or talk to Pi's remote procedure call (RPC) stream directly. Closing the frontend closes that socket and terminal interface only.

### The daemon is the single state writer

[`createDaemonRuntime`](../runtime/daemon.mjs) owns the session registry, list invalidation, the in-memory normalized viewer read models, and worker routes. It records nothing durable about a command: the owning worker's replay log is the acceptance boundary, described in [`docs/command-acceptance.md`](command-acceptance.md). It authenticates local socket connections with `daemon/control.token` and reconciles durable state before accepting mutations.

Every authenticated client may write to every session. There is no access role: a dashboard's `attach` records that a session is open on that connection, subscribes it to viewer state, and starts a worker for a session whose own has exited. Concurrent commands on one session are ordered by that session's coordinator, so a second dashboard adds ordered commands rather than racing the first. An attachment is connection state and nothing more; it is never persisted, and it ends when its socket does.

All session-record writes run in this process through [`RegistryStore`](../runtime/registry-store.mjs). Per-session lifecycle operations use [`runSessionLifecycle`](../runtime/registry-store.mjs), which serializes changes for one session without serializing unrelated sessions.

### A worker keeps one Pi process alive

[`WorkerSupervisor`](../runtime/worker-supervisor.mjs) starts one detached [`runtime/worker.mjs`](../runtime/worker.mjs) process for a session. [`runInstalledPiWorker`](../runtime/installed-pi-worker.mjs) then starts the installed executable with arguments built by [`piRpcArgv`](../runtime/pi-rpc-adapter.mjs):

```text
pi --mode rpc --session <canonical-session-file>
```

The worker owns Pi's stdin, stdout, and stderr pipes. Pi treats the RPC stdin pipe as its lifetime. If the process holding that pipe disappears, the pipe closes and Pi exits. A live parent is therefore required for every session. The worker is the acceptance boundary for the operator's text: it fsyncs that text to its own replay log before it writes to Pi and after Pi answers, and forwards commands and Pi frames or events.

**The worker owns its socket and the daemon connects to it.** The daemon names the path before it spawns the worker and records it against the run in `daemon/workers.json`; [`listenForDaemon`](../runtime/worker-socket.mjs) creates the file, at mode 0600 under `daemon/workers/`, and the worker refuses any connection that does not open with that run's token. A replacement daemon therefore reads the roster and connects, so adoption is a reconnect rather than a negotiation over a connection the worker had to start, and the daemon stops being the process that must exist first. Nothing creates the socket until the worker listens, so a daemon that dies between naming the path and spawning leaves no file a later daemon could read as a live worker.

Two bounds sit on that boundary, and they are the same number: the launch's `startTimeoutMs`, passed to the worker as `--startup-deadline-ms`. Past it the daemon stops retrying its connect and fails the launch with `WORKER_SOCKET_UNREACHABLE`; past it a worker nobody connected to writes `WORKER_STARTUP_DEADLINE` to its own stderr, removes its socket, and exits. That bound covers the launch handshake only. Once readiness is sent it is cleared, and from then on the worker outlives daemon absence indefinitely with no timeout of its own, which is the divergence recorded in `AGENTS.md`.

The daemon may exit without stopping a worker. The worker keeps listening, remains Pi's parent, and is reached again by the next daemon. Closing the frontend or restarting the daemon therefore does not make Pi depend on a terminal or daemon socket. A route that drops while this daemon is still running is re-opened by [`RecoveredWorkerRouter`](../runtime/reconciliation.mjs) rather than left closed, because the worker is still listening and a live session must never go quiet without saying so.

## The daemon runs on demand

There is no resident daemon. [`createIdleExit`](../runtime/idle-exit.mjs) ends one that has had nothing to do for [`DEFAULT_IDLE_EXIT_MS`](../runtime/idle-exit.mjs), 30 seconds, and `--idle-exit-ms` or `PI_AGENTS_IDLE_EXIT_MS` selects another window. Zero keeps the daemon resident and now has to be asked for; a value that cannot be read refuses the start rather than silently staying up forever. A dashboard, or any command that needs a daemon, starts one through [`runDaemonCommand`](../cli/daemon-commands.mjs) and finds the current build rather than whatever build a long-lived process loaded.

Idle is decided by `idleHold` in [`runtime/daemon.mjs`](../runtime/daemon.mjs), which names the first reason this daemon must stay up: a scheduled worker replacement, a launch in progress, a command whose bytes are with a worker that still owes a reply, or a connected dashboard. No connected client is necessary but not sufficient, because a worker holds a connection too: only connections that authenticated as `frontend` count, so a session with nobody watching it is not a client. Each accepted connection re-arms the window before it authenticates, which is what keeps a liveness probe from being followed by an exit and then the connect that probe was for.

Live workers deliberately do not hold the daemon open, which is Claude Code's answer as well. A worker is Pi's parent, survives daemon absence indefinitely, keeps its live tail, and keeps writing its durable delivery replay log, while Pi keeps writing the canonical session file; none of that needs a daemon. Holding the daemon open for them would mean any operator with one running session never gets an on-demand daemon at all. Nothing has to wake the daemon for a session to keep working: the worker keeps listening on its own socket with no timeout, and the operator's next command starts a daemon that connects to it, ingests the tail it replays, and re-derives task state from Pi.

An idle exit signals nothing. It resolves the same stop the daemon takes from `SIGTERM`, and `WorkerSupervisor.close` drops the daemon end of every route without touching a process group, so no session ends and no live session becomes unreachable.

## A launch moves through five boundaries

1. [`DashboardController.submitComposer`](../app/list/dashboard.mjs) treats a nonempty, non-slash line as a launch. A launch that is refused, or that fails on the transport, is one failure raised to one caller, which hands the typed prompt back to the composer. The frontend canonicalizes the working directory and asks for exact confirmation when shared-directory isolation is selected.
2. [`createDaemonClient.launch`](../app/daemon-client.mjs) sends a version 1 `launch` request. The daemon admits the requested model against Pi's own catalog: a model Pi does not offer ends the launch at `FAILED` with `MODEL_UNKNOWN` and prepares nothing, so no record, Pi file, worktree, worker, or row exists to clean up. The frontend picker is an earlier check, not this one. A catalog Pi cannot list refuses nothing; it is recorded as a `model_catalog_unavailable` diagnostic and Pi decides what it accepts.
3. [`createLaunchResolver`](../runtime/launch-resolver.mjs) repeats trusted isolation checks in the daemon. It creates a managed worktree or confirms the shared directory, asks Pi's public `SessionManager` for a canonical session file, and creates the initial `SessionRecord`.
4. [`WorkerSupervisor.launch`](../runtime/worker-supervisor.mjs) resolves and probes the Pi executable, acquires the ownership lease, reserves the run by its per-run token and the socket path that run's worker will listen on, starts the detached worker, and verifies the worker and Pi process identities. The daemon then connects to that socket, retrying while the spawned worker is still on its way to `listen`, and authenticates with the per-run token. The worker answers with `hello`, and the launch binds it only if the claimed PID, process start identity, and process group match the process it spawned — the PID is already known here, because the daemon is the side that connects. `activate`, `pi_child`, `child_bound`, and `worker_ready` all travel on that one socket. The worker opens Pi in RPC mode and checks `get_state` against the canonical session path, and reports the model that state named in its `worker_ready` frame.
5. The supervisor registers both process identities, adopts the startup connection as the session's route, and only then persists readiness. That same write records the model Pi reported. A row shows a model only after Pi names one: the requested model reaches Pi through the worker's arguments and never the record, so a launch that fails before Pi runs shows no model at all. The daemon delivers the launch prompt over that route as the first durable `prompt` command, outside the session lifecycle lock, because the worker's reply re-enters that lock. The list replaces its temporary `STARTING` row with the session record received from the event stream.

A failure before a child owns the session marks the prepared record `FAILED`. Delivery that cannot be proved is answered `DELIVERY_UNKNOWN`; the daemon does not guess whether Pi received it, and it keeps no record of the attempt to come back for. A launch whose answer is lost is not replayed: the row it created is what the operator reads, and a reissue is a second session he can see and remove.

## A worker behind the daemon's release is replaced only at an idle boundary

A daemon adopts every protocol-compatible live worker before it compares releases, so an upgrade never refuses a running session. A worker whose recorded `cliVersion` is behind the daemon's, or absent, is then replaced by [`replaceStaleWorker`](../runtime/daemon.mjs), which runs once, serialized under the session lifecycle lock, from one of two boundaries:

- Pi settling the run. [`sessionEventForPiEvent`](../runtime/session-event-mapping.mjs) maps `agent_settled` to `TURN_COMPLETED`, and the row it reduces to opens the boundary. Only that reduced record decides: [`idleForRespawn`](../runtime/daemon.mjs) requires `taskState: READY`, `processState: LIVE`, and no blocking user-interface request. Terminal bytes and the canonical Pi session file may never open it, and `WAITING` is Pi blocked on a person rather than an idle session.
- `pi-agents respawn <full-session-id> --revision <n> --yes`, which takes the same full identifier, exact revision, and explicit confirmation as `stop` and `rm`. It refuses a session that is not idle rather than interrupting a running turn.

At the boundary the operation re-reads every fact it rests on: the revision, the adopted route, both recorded process identities, the release, and the idle state. A worker newer than the daemon is never downgraded: the automatic boundary passes over it, and an explicit `respawn` refuses it. Every refusal the guarded operation reaches is recorded as a daemon diagnostic and leaves the worker running.

Before anything is signalled, the run's private metadata gains `pendingRespawn: "upgrade"`, so a daemon that dies mid-replacement resumes the guarded operation after it has adopted that worker again. The replacement then stops the worker through the same exact-identity boundary Stop uses, forgets the run, and launches a new one. Automatic replacements are bounded to three in flight across sessions, so one upgrade does not restart every idle session at once, because each replacement costs a cold start. The bound delays a replacement; it never cancels one. A session that settles while three are already running is deferred and recorded as a `respawn_deferred` diagnostic, and the next replacement to finish re-decides it from a freshly read record, so a burst wider than the bound still ends with every stale worker replaced rather than leaving the last of them on old code.

The replacement is visible while it runs, because it takes as long as a cold start on a session the operator was using. The same operation reduces `WORKER_REPLACING` onto the row before it signals, and the `replacing` activity that writes reads as `STARTING` in the list for as long as the restart takes, exactly as a launch does; a replacement that stops short of proof restores the activity it found. Once the old worker is provably gone it appends one notice to the session's normalized viewer stream, so an open viewer says what the pause is. Both surfaces come from that one structured transition, never from terminal bytes or from how long a reply is taking.

See [`docs/reference/claude-code-behavior.md`](reference/claude-code-behavior.md#release-changes-adopt-workers-before-replacing-them).

## The list is invalidated; the viewer is rebuilt

The session list carries no history. [`DashboardController.open`](../app/list/dashboard.mjs) sends `subscribe_list_changes` first, sets one dirty flag, then reads `get_state`. A change the daemon publishes while that read is in flight arrives as a payload-free `list_changed` frame, which only sets the flag again, so the read loop performs one more read and stops. Any number of invalidations between two reads mean the same single read: there is no queue, no cursor to fall behind, and nothing that grows with a burst.

Every successful `get_state` result carries a `cursor`, the pair `daemonEpoch` and `sequence`, which is how far the daemon's list had advanced when it read those rows. The daemon reads that cursor before the registry, never after, so a snapshot never claims to cover a change it does not contain. The cursor lives only in daemon memory and in the dashboard's memory; nothing replays from it and it does not survive a daemon restart.

The daemon publishes nothing else about the list. There is one list subscription protocol, `subscribe_list_changes`, and no persisted list history: a change advances the in-memory cursor and broadcasts one `list_changed` frame.

Retiring that history broke the frontend protocol, removing the access role from the `attach` request and its reply broke it again, retiring `get_viewer_snapshot` with the viewer resume cursor broke it a third time, retiring `resolve_delivery` with the delivery stage every command answer carried broke it a fourth, and inverting the worker socket broke it a fifth, so the daemon and every dashboard restart together. The socket authentication frame from a frontend declares `clientProtocol: 6` ([`CLIENT_PROTOCOL`](../shared/contracts.mjs)) and the process-scoped `attachId` described below, and the daemon refuses the first request on a frontend connection that declares anything else with `UNSUPPORTED_CLIENT_PROTOCOL`, naming the protocol it speaks. It refuses that request and keeps the connection: closing it made an older client reconnect and resubscribe, which turns one refusal into a reconnect storm. Control frames carry no `clientProtocol` on purpose: the liveness probe in [`probeDaemon`](../cli/daemon-commands.mjs) and the stop frame in `requestDaemonStop` are how a client from this release reaches a daemon from the previous one.

Probing is not restarting, and for one release that difference stranded an operator. `daemon stop`, and the stop half of `daemon restart`, also opened a frontend connection to read `get_state` for the live-worker check, and an earlier daemon refuses that connection's authentication frame outright for its unknown `clientProtocol` key. A restart's stop now reads no rows at all, because it stops the daemon whatever they say. A `daemon stop` that cannot read them stops the daemon anyway: the signal goes to the daemon's own process group and workers hold their own, so no session ends. Only `--stop-workers` still needs those rows, and it refuses with the release that would not answer. Any CLI command refused at that handshake reports `DAEMON_FROM_EARLIER_RELEASE` and names `pi-agents daemon restart`, but only once [`describeAuthenticationRefusal`](../cli/session-commands.mjs) has confirmed the cause by offering the version-and-token frame every release accepts; a daemon that refuses that one too was handed a token it does not hold, and keeps today's refusal.

There is no viewer resume cursor. `subscribe_viewer` answers with the snapshot its subscription continues, both taken in one step under that session's frame lock, so nothing can be published between them and nothing needs to be retained to replay it. `cursor` on a snapshot or an event says how far this daemon's stream has advanced within its epoch; nothing replays from it and it restarts at zero with the daemon.

Opening that subscription is a tracked request, as the list's is, and [`createDaemonClient`](../app/daemon-client.mjs) registers the subscriber before it sends the request, so an event the daemon writes in the same chunk as its answer is queued rather than dropped. A refusal ends the subscriber with that error and reaches the caller that opened it, which is the whole subscription: `subscribeViewer` answers with the snapshot or raises the refusal, never with a reader on a stream the daemon never opened. Sent fire-and-forget, those refusals reached the response dispatcher, matched no pending request and were dropped, which left the operator reading a transcript that had stopped on a connection still reporting itself healthy. A stream that stops after it was accepted says so on its own `viewer_stream_failed` frame ([`parseViewerStreamFailed`](../shared/contracts.mjs)), for the same reason: by then the establishing request is answered, and a second response frame belongs to no pending request. Three things send it — a subscriber past its bounded queue, a session rebuilt from Pi's file and its worker's tail, and a lost connection — and [`ViewerController.streamFailed`](../app/viewer/viewer-controller.mjs) answers all three the way the list answers a burst, with one reload from a fresh snapshot. A second refusal with no event in between is not reloaded again: the viewer records the daemon's own code as a transcript error, says the transcript stopped, and stops drawing a running turn from the last state it received.

[`ViewerController.open`](../app/viewer/viewer-controller.mjs) builds its transcript from the subscription's snapshot and then reads that subscription's events. Nothing about a viewer is durable: no acknowledgement, no cursor, and no transcript.

The frontend keeps its selection, view state, launch draft, and viewer drafts in its own process memory and writes none of them. Three dashboards therefore hold three independent screens, and a dashboard that dies loses an unsubmitted draft. Two identities go to the daemon and mean different things: the installation's stable `clientId` in every request envelope, which with the request ID is the identity a worker's replay log keys a command by, and a `attachId` generated once per dashboard process and declared in the socket authentication frame, which is what the daemon binds this connection's open sessions to.

### The worker holds the live tail; Pi's own file holds the history

There is one transcript on disk and Pi owns it. A viewer's completed history is read from the canonical session file on every subscription through [`createSessionHistoryReader`](../runtime/session-history.mjs), with its no-follow open and its device-and-inode check. The frames Pi has not written there yet live in the worker's [`createLiveTail`](../runtime/worker-live-tail.mjs), bounded at 262,144 bytes of serialized frame, which is what Claude Code's pseudo-terminal host retains for the same purpose. [`createViewerNormalizer`](../runtime/viewer-normalizer.mjs) merges the two into the version 1 shapes in [`shared/viewer-contracts.mjs`](../shared/viewer-contracts.mjs), and one [`createViewerStream`](../runtime/viewer-stream.mjs) per session numbers and broadcasts them. Frontends never receive raw Pi RPC frames.

The worker replays that tail as one `pi_tail` frame on every connection after its launch, written in the same step as its readiness frame so no live frame can interleave. The daemon rebuilds that session from the canonical file plus the tail, ends every subscriber with `VIEWER_RESYNCHRONIZED`, and each viewer answers with one fresh snapshot. Rebuilding from scratch is what makes a replay idempotent: the normalizer's message fingerprint collapses a message that appears in both sources, but nothing collapses one frame ingested twice into the same normalizer. A daemon restart therefore keeps partial streaming text, which no durable store could do, because the process holding that text is the one that never restarted.

The tail drops its oldest frames when it is full, except an unresolved Pi dialog request: Pi is blocked on a person until that request is answered, and a frontend that attaches later can only learn about it from the tail, so it is pinned until Pi resolves it or the byte bound is down to nothing else. A rebuild from a truncated tail serves Pi's completed history plus the newest live frames, and the daemon records a `viewer_tail_truncated` diagnostic with the dropped and retained counts. The operator loses partial text older than the bound; the session resynchronizes rather than freezing or failing.

## Durable state is grouped by purpose

[`resolveDashboardRoots`](../runtime/paths.mjs) selects `$PI_AGENTS_STATE_DIR`, or `${XDG_STATE_HOME:-$HOME/.local/state}/pi-agents`. The main contents are:

```text
<state root>/
  dashboard.json
  daemon/
  sessions/
  queue/
  index/
  runs/
```

- `dashboard.json` is the optional schema version 2 configuration.
- `daemon/` stores daemon identity and coordination data. This includes `pid.json`, `control.sock`, `control.token`, `epoch`, `lifecycle.lock`, worker routes in `workers.json`, one mode-0600 socket per live worker under the mode-0700 `workers/`, summary settings, request result stores, the latest `reconciliation.json`, and `startup.log`. `control.sock` carries frontend and control connections only; a worker never connects to it. Daemon diagnostics, including a refused worker replacement, are one JSON line each on the daemon's stderr, which `daemon/startup.log` captures. `workers.json` is a mode-0600 owned file because it holds each run's private socket token. A run is written there before its worker is spawned and both process identities are absent until the launch binds them. The token is never rotated during adoption, so a replacement daemon authenticates the same live run; a respawn mints a new one, and terminal reconciliation removes the whole entry. Each entry also records `socketPath`, the socket its worker listens on, which the daemon chose before that worker was spawned; the worker socket arrangement as integer `proto`, 2 in this release; the release the worker was spawned from as optional `cliVersion`; and the `routeGeneration` of its last successful adoption. An entry whose `proto` is not 2, or which carries no `socketPath`, belongs to a worker from the previous release: it listens on nothing, so this daemon cannot reach it. That is reported, never signalled — see below. An absent `cliVersion` means the release is unknown. An entry gains `pendingRespawn: "upgrade"` before the daemon signals a replacement, and loses it with the entry when that run ends.
- `sessions/<sessionId>.json` is the daemon-owned registry. Each version 1 record contains immutable session identity, revision, display state, isolation, ownership, and verified runtime identity when available.
- `index/` holds nothing at all. A new root has no `index/` entries, and a root that still carries `index/viewer/*` or `index/events.jsonl` from an earlier release is never opened, parsed, migrated, or deleted: this release keeps no durable viewer transcript, so no code names that directory. The same is true of `daemon/event-acks.json`, `frontend-state.json`, and `daemon/attachment-results.jsonl`.
- `queue/` is not created and holds nothing. `queue/commands.jsonl` was the daemon-wide command journal; the owning worker's replay log is the acceptance boundary now, so no code names that directory. A root that still carries it, or the `daemon/launch-results.json` and `cli/pending/*.json` that existed only to give that journal a stable retry identity, is never opened, parsed or deleted, and a state-root migration drops all three rather than carrying them forward.
- `runs/<hash>/` holds one worker's stdout, stderr, durable Pi-delivery replay log, and rotating raw RPC and Pi stderr diagnostics. That replay log is the acceptance boundary for the operator's text, and it is the only durable copy of it before Pi has it: see [`docs/command-acceptance.md`](command-acceptance.md). The session record keeps that directory name as root-relative `runHash`, so a renamed state root still resolves its own diagnostics.

Two owned paths are outside the state root. Canonical Pi session files remain in the location chosen by Pi's `SessionManager`. Managed worktrees live under Pi's agent directory at `pi-agents/worktrees`.

## Changes must preserve these invariants

- **A worker this daemon cannot reach is reported, not signalled, and never blocks the start.** Every other recovery conflict refuses the daemon start; `WORKER_UNREACHABLE` does not, because refusing would take every other session on the root down with one worker. The daemon records a `worker_unreachable` diagnostic naming the fix, adds `workerUnreachable` to that session's row on every `get_state`, and refuses each command on it by that code with the fix in the message. The worker keeps running and keeps Pi, `stop` still works because it signals the recorded process identity and never needs the route, and reopening the session afterwards starts a worker this daemon can reach.
- **An idle exit is not a stop.** The daemon exits only when `idleHold` names nothing. It never signals a worker, never ends a session, and never leaves a live session unreachable: the next command starts a daemon that adopts it.
- **The daemon is the only writer of session records.** Frontends and workers send versioned messages. Registry creation, updates, and removal stay in the daemon through [`RegistryStore`](../runtime/registry-store.mjs).
- **One daemon owns a state root, and a replacement waits for proof.** `daemon stop`, and the stop half of `daemon restart`, report success only after the published PID, process start identity, and process group stop matching in [`waitForProcessExit`](../cli/daemon-commands.mjs). An absent `daemon/pid.json` is not that proof, because the daemon removes it as the last step of its own shutdown and can still be running afterwards. `daemon start` with no explicit root resolves it through [`adoptRenamedStateRoot`](../runtime/state-root-adoption.mjs), so every start path adopts, defers, or refuses rather than opening an empty root beside existing sessions. Its wait for a healthy endpoint runs to a 90 s deadline, so [`waitForStatus`](../cli/daemon-commands.mjs) reports the wait on the caller's error stream from three seconds on: the command's own result is written only after that wait ends, and the standalone dashboard starts the daemon before it opens the interface.
- **Ownership outlives uncertainty.** Release ownership only after both the supervisor and its Pi child are provably gone. PID alone is insufficient. [`WorkerSupervisor`](../runtime/worker-supervisor.mjs) compares PID, process start identity, and process-group ID, and retains the lease when a child identity is live or ambiguous.
- **Delete only forgets dashboard state.** Delete removes the inactive `SessionRecord`, and the daemon has no seam that could unlink the canonical Pi session file or remove a worktree. Worktree cleanup remains a separate operation in [`isolation/cleanup.mjs`](../isolation/cleanup.mjs).
- **Pi lifecycle event mapping has one home.** [`sessionEventForPiEvent`](../runtime/session-event-mapping.mjs) is the only mapping from Pi RPC events to dashboard session-state events. Viewer frame normalization is the separate read model in [`runtime/viewer-normalizer.mjs`](../runtime/viewer-normalizer.mjs).
- **A revision guard covers the facts an operation uses.** Stop rechecks the exact ownership and process identity at the signaling boundary. Delete rechecks inactive state and record identity. The frontend may retry after unrelated display metadata changes only while the requested destructive action is still the same. Adopting a worker is not a session change, so `workerCliVersion`, `stale`, and `routeGeneration` are added to a row when `get_state` reads it ([`withWorkerAdoption`](../runtime/daemon.mjs)) rather than written to the record: a revision invalidated by every daemon restart would teach the operator to retry past the guard.
- **Background work stays outside operator locks.** Summary inference runs before the short lifecycle write section in [`refreshSummaries`](../runtime/daemon.mjs). Viewer frame ingestion, a tail rebuild, and opening a subscription all use the separate frame coordinator in [`RecoveredWorkerRouter.runFrame`](../runtime/reconciliation.mjs), which is what makes a snapshot and its subscription one step. Do not hold a lifecycle or route lock across work that an operator keystroke does not depend on.
- **A failure is scoped to what it can be attributed to.** A response frame [`createDaemonClient`](../app/daemon-client.mjs) cannot parse rejects that one request with `MALFORMED_RESPONSE` and keeps the connection, because destroying it made the reconnect resend the request that provoked the frame. Authentication failure, a transport error, and an unparseable frame that belongs to no request stay fatal.
- **Waiting for another process is bounded, and expiry is ambiguous.** [`PiRpcAdapter`](../runtime/pi-rpc-adapter.mjs) expires one unanswered Pi command after 120 seconds with `RPC_TIMEOUT` and stays usable; the daemon expires one unanswered worker request after 300 seconds. Both report `DELIVERY_UNKNOWN`, never `FAILED`, because the bytes may already have reached Pi.
- **The owning worker is the acceptance boundary.** The operator's text is durable when that worker has fsynced it, before any Pi write. The daemon adds no record of its own, a request identity already acknowledged is never written to Pi twice, and one recorded ambiguous is never silently retried. [`docs/command-acceptance.md`](command-acceptance.md) states what every crash point costs; a change to any of those guarantees belongs in that file first.
- **Every process boundary is a versioned contract.** Frontend requests, daemon responses, and list events use [`shared/contracts.mjs`](../shared/contracts.mjs). Viewer snapshots and events use [`shared/viewer-contracts.mjs`](../shared/viewer-contracts.mjs). Worker socket frames and replay records also carry version 1, and the arrangement those frames travel on is `WORKER_SOCKET_PROTOCOL` in [`runtime/worker-socket.mjs`](../runtime/worker-socket.mjs), recorded per run as `proto`. Change parsers, producers, consumers, and contract tests together.

## Directory map

- `app/list/` contains list state, input, layout, overlays, launch composition, and daemon adaptation. Start with [`app/list/dashboard.mjs`](../app/list/dashboard.mjs).
- `app/viewer/` contains the Pi-style transcript, editor control, overlays, and viewer slash handling. Start with [`app/viewer/viewer-controller.mjs`](../app/viewer/viewer-controller.mjs).
- `app/daemon-client.mjs` is the whole daemon-facing surface of both the frontend and the command line: reconnecting socket transport, subscription queues, and every operation the list and the viewer send. There is one client and one shape; the list and the viewer hold the same object, and every command in `cli/` runs the same client with `reconnect: false`, held open for exactly one operation. `app/standalone.mjs` and `app/list/standalone-list.mjs` assemble the terminal application.
- `runtime/` contains the daemon, registry, recovery, worker supervision, Pi RPC adapter, normalization, and durable stores. Start with [`runtime/daemon.mjs`](../runtime/daemon.mjs).
- `shared/` contains strict contracts shared across process boundaries.
- `isolation/` contains launch preflight, managed worktrees, ownership locks, and explicit cleanup.
- `cli/` contains the operator verbs `agents`, `attach`, `logs`, `stop`, `rm`, and `respawn`, plus administrative daemon and session-recovery commands. What it owns beyond argument parsing, exit codes and its JSON output is the private client identity file, a bounded per-command deadline, and the classification that decides whether a lost answer to a destructive command may already have run. `bin/` contains the installed executable entry point.
- `test/` contains cross-module integration and terminal acceptance tests. Unit tests sit beside their source as `*.test.mjs`.
